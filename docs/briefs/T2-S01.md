# T2-S01 — probe + 2E generator + sealed key + fixtures

Repo: td-2-soc · Environment: td-2-soc · Day: D0 · Time box: 90 minutes · Credit cap: $8

## Goal
Record what this cloud machine can do (`probe`), then build the 2E Blind Hunt data: a seeded Python generator (plain code, no AI in the data) that writes about 5,000 fictional Entra-style sign-in and audit events over 14 days for Maple Harbour Credit Union, with 5 hidden account-takeover sequences and at least 8 benign look-alikes. Seal the answer key so Eojin can hunt without knowing the answers, and produce a small unsealed `fixtures/` dataset with known answers for automated tests. Terms: "Entra" is Microsoft's cloud sign-in service; "seeded" means the same random seed always produces the same output; the "answer key" is the list of which events are the hidden takeovers.

3. `builder`: project skeleton. Create `pyproject.toml` with `[tool.ruff]` (`target-version = "py312"`, `line-length = 100`) and `[tool.pytest.ini_options]` registering the marker `kusto: needs the Kusto emulator on KUSTO_URL` (used from T2-S02 on). Repo convention from now on: test file basenames are unique across the whole repo (`test_2e_generator.py`, later `test_2h_headers.py`, …), because `pytest -q` from the root collects every project folder and its default import mode rejects two files with the same name. 4. `builder`: the generator, `2e-blind-hunt/generate.py`, standard library only (`random`, `json`, `datetime`, `argparse`, `hashlib`, `uuid`), no network, no AI. CLI: `--seed <int>` (required), `--out-dir <dir>` (writes `signin.jsonl` and `audit.jsonl`), `--labels-out <path>` (the plaintext key; written only where asked), `--days` (default 14), `--events` (target total, default 5000), `--takeovers` (default 5), `--lookalikes` (default 8). Requirements:
   - 50 fictional staff at `mapleharbour.example` (first.last UPNs), departments (branch, lending, finance, IT, helpdesk ×2, executives), a "usual" device id, browser/OS, usual IP and usual location (mostly Toronto / Ontario / CA; a few remote-in-Canada). Phone numbers, if any appear in notes, are `555-01xx`. All IP addresses come from the documentation ranges reserved by RFC 5737 (`192.0.2.0/24`, `198.51.100.0/24`, `203.0.113.0/24`) so no address can point at a real machine; attacker "locations" are outside Canada but the IPs still come from those ranges.
   - Field names exactly: `TimeGenerated` (ISO 8601, UTC, `Z` suffix), `UserPrincipalName`, `IPAddress`, `Location` (object: `city`, `state`, `countryOrRegion`), `AppDisplayName`, `ResultType` (`"0"` = success; a small fixed set of non-zero strings for failures, each explained in the README with `TODO(verify)` against Microsoft's sign-in error code list), `AuthenticationRequirement` (`singleFactorAuthentication` / `multiFactorAuthentication`), `DeviceDetail` (object: `deviceId`, `displayName`, `operatingSystem`, `browser`, `trustType`), `OperationName`, `InitiatedBy` (object: `user` with `userPrincipalName` and `ipAddress`), `TargetResources` (list of objects: `displayName`, `userPrincipalName`, `modifiedProperties` list), `CorrelationId` (UUID string). Sign-in rows carry the sign-in fields; audit rows carry the audit fields; both carry `TimeGenerated`, `CorrelationId`. Exact Entra spellings of `OperationName` values (`Reset password (by admin)`, `User registered security info`, `Add member to role`, `Update user`) are to be marked `TODO(verify)` in the README, not claimed.
   - Normal life first: working-hours sign-ins per person per weekday with jitter, some weekend and evening activity, routine failures (wrong password then success), routine audit events (admin adds a user to a group, self-service MFA registration for new hires).
   - Hidden takeovers (exactly `--takeovers`, from a `sequences` list so the labels are exact): each is (a) audit: one of the two helpdesk accounts performs the admin password reset on the target with a ticket note in `modifiedProperties` that lacks the verification marker (see look-alikes), (b) audit: the target "registers security info" (new MFA method) minutes to hours later, (c) sign-in: success from a device id / IP / location never seen for that user, `multiFactorAuthentication` satisfied, (d) a privileged action: `Add member to role`, a sign-in to the `Core Banking Admin` app, or `Update user` changing the recovery email. Vary the gaps (one sequence spans two days), the targets (one privileged user, one finance clerk, one executive assistant …), and the hour of day. Record for each: id (`TK1`…), user, start, end, the CorrelationIds of its events, and a one-sentence "why it is a takeover".
   - Benign look-alikes (at least `--lookalikes`, each with an id `LA1`… and a one-sentence "why it is benign"), each distinguishable from the data alone: lost phone → helpdesk reset whose ticket note contains the verification marker (`verified: callback to number on file`) → new MFA → sign-in from the user's *known* device; new hire → first sign-in from a new device + MFA registration, no reset; travelling user → new location, known device; scheduled role change by an IT admin during business hours; self-service password reset; MFA re-registration after a phone upgrade from the known IP; helpdesk reset followed by a sign-in from the known device only; VPN causing a location change on a known device; two or three benign helpdesk resets whose ticket note lacks the verification marker (a rushed agent), followed only by sign-ins from the user's known device and no new MFA method, so the marker alone never decides a case.
   - No tells: hidden events must use the same pools, formats and second-level jitter as normal events; the words `takeover`, `attacker`, `malicious`, `lookalike`, `look-alike`, `TK` and `LA` followed by a digit must not appear anywhere in the data files. Output rows are sorted by `TimeGenerated`.
   - Labels file (`--labels-out`): `{"seed": <int>, "generated": "<ISO date>", "takeovers": [...], "lookalikes": [...]}` as above.
5. `builder`: `scripts/score_my_labels.py --labels <my-labels.json> --key <decrypted-key.json>`: prints precision and recall of the labelled takeovers (match rule: same `UserPrincipalName` and time windows overlap), lists matched / missed / extra, and never prints the key's contents beyond ids and users of misses. Also `2e-blind-hunt/my-labels.template.json` (`{"takeovers": [{"id": "", "user": "", "start": "", "end": "", "evidence": [], "summary": ""}]}`) and `2e-blind-hunt/incident-report-template.md` (what happened, timeline, evidence rows, impact, containment recommended, what the helpdesk should have asked — in plain words).
6. `builder`: tests in `2e-blind-hunt/tests/test_2e_generator.py` with a fixed test seed and a temp directory: same seed twice → byte-identical files; total rows within ±10% of `--events`; `TimeGenerated` span is 14 days; every row is valid JSON with the agreed fields; every UPN ends in `@mapleharbour.example`; every IP is inside the RFC 5737 ranges; the labels file has exactly 5 takeovers and ≥ 8 look-alikes whose CorrelationIds all exist in the data; the no-tells check; `score_my_labels.py` returns precision = recall = 1.0 when the key is scored against itself and 0.0 for an empty labels file. Run `ruff check .` and `pytest -q`; both must pass.
7. `chores`: generate the unsealed fixtures with a fixed, committed seed: `python 2e-blind-hunt/generate.py --seed 7 --days 3 --events 300 --takeovers 2 --lookalikes 3 --out-dir fixtures --labels-out fixtures/expected.json`. This labels file IS committed in plain text: it is the answer sheet for CI tests, not for the hunt. Confirm `fixtures/expected.json` lists 2 takeovers and ≥ 3 look-alikes.
8. Director (no subagent): generate the real dataset and seal the key in ONE Bash call, inside a subshell, so the passphrase lives only in a shell variable that disappears when the subshell ends, and never appears in a file or a later command line. The seed is random and is NOT committed either (a public seed plus a public generator would regenerate the key):
   ```bash
   (
     set -e
     SEED="$(python3 -c 'import secrets; print(secrets.randbits(128))')"
     PASS="$(openssl rand -base64 18)"            # 24 characters
     python3 2e-blind-hunt/generate.py --seed "$SEED" --out-dir 2e-blind-hunt/data --labels-out /tmp/key.json
     sha256sum /tmp/key.json | awk '{print $1}' > 2e-blind-hunt/data/answer-key.sha256
     openssl enc -aes-256-cbc -pbkdf2 -salt -in /tmp/key.json -out 2e-blind-hunt/data/answer-key.enc -pass pass:"$PASS"
     echo "round-trip hash: $(openssl enc -d -aes-256-cbc -pbkdf2 -in 2e-blind-hunt/data/answer-key.enc -pass pass:"$PASS" | sha256sum | awk '{print $1}')"
     echo "saved hash:      $(cat 2e-blind-hunt/data/answer-key.sha256)"
     (shred -u /tmp/key.json 2>/dev/null || rm -f /tmp/key.json)
     sha256sum 2e-blind-hunt/data/signin.jsonl 2e-blind-hunt/data/audit.jsonl > 2e-blind-hunt/data/dataset.sha256
     echo "STORE THESE NOW IN YOUR PASSWORD MANAGER (shown once, never written to a file):"
     echo "  2E passphrase: $PASS"
     echo "  2E seed:       $SEED"
   )
   ```
   (seed raised from randbelow(10**9) to 128 bits by Eojin's decision, 2026-10-22)
   The two hashes must be equal. If the block stops early (`set -e`), delete everything under `2e-blind-hunt/data/` and run it again: a half-sealed key with a passphrase nobody saw is useless. Then `ls /tmp/key.json` must fail, and `git status` must show only `data/signin.jsonl`, `data/audit.jsonl`, `data/answer-key.enc`, `data/answer-key.sha256`, `data/dataset.sha256` under `2e-blind-hunt/data/`. Ask Eojin to confirm in chat that he stored both values, then check his copy: he types the stored passphrase back into the chat, and the director runs one command that decrypts with what he typed and prints only `MATCH` or `NO MATCH` against `answer-key.sha256` (that one command line is the only place the passphrase appears; nothing is saved). `NO MATCH` → he checks for a mistyped character and tries once more; still `NO MATCH` → delete everything under `2e-blind-hunt/data/` and run step 8 again. Do not paste the passphrase or seed into any file, commit message, verify report or caveat.
9. `builder`: `2e-blind-hunt/README.md` in plain English: what the data is (fields, with the `TODO(verify)` notes), what is hidden (counts only), how to hunt (jq / Python / spreadsheet now; KQL on the emulator after T2-S02), the rule "commit `my-labels.json` and the 5 reports BEFORE decrypting", the unseal commands (below, under Eojin's part), the match rule used by the scorer, `dataset.sha256` and `answer-key.sha256` and what each proves, a "What Claude did / what Eojin did" section, limits (synthetic data, imitated schema, no real geolocation).
10. `verifier`: check every acceptance criterion below, write `docs/verify/T2-S01.md`.
11. Director: `wrap` (RUN-SHEET, COSTS with the balances Eojin reads out, AI-USE, CAVEATS; push `t2-s01-blind-hunt-generator`; print the PR title and body).

- PyPI unreachable or `openssl` missing: stop and report; do not substitute a Python crypto library without asking.
- The generator cannot reach ~5,000 events with 5 takeovers and 8 look-alikes within about 60% of the cap: stop and propose a smaller dataset (for example 3,000 events) for approval.
- Any doubt that the passphrase, seed or plaintext key touched a file, a commit, or a command line that could be logged: stop, tell Eojin, delete the affected files, and redo step 8 with a new passphrase and seed.

# T2-S02 — 2H detections + Kusto CI

Repo: td-2-soc · Environment: td-2-soc · Day: D2 · Time box: 150 minutes · Credit cap: $15

## Goal
Build the Takeover Detection Pack: KQL detection queries (KQL is the query language of Microsoft Sentinel and Azure Data Explorer), each with a YAML header describing what it catches and which AL26-010 control it supports, plus a pytest harness that loads the unsealed `fixtures/` into the local Kusto emulator (a free Docker container running the KQL engine), runs every detection, and proves the known takeovers are caught and the look-alikes are not. Make the `kql` CI job green. Eojin's blind hunt on the full 2E data is still running: nothing in this session may run against, print or commit results from `2e-blind-hunt/data/`.

## Steps
1. Director: Plan mode. Read this brief, check Needs, propose the plan (emulator path or fallback path), wait for approval. `git checkout -b t2-s02-detection-pack`.
2. Director (emulator path): start the emulator and wait for it:
   ```bash
   docker run -d --name kusto -e ACCEPT_EULA=Y -m 4G -p 9000:8080 mcr.microsoft.com/azuredataexplorer/kustainer-linux:latest
   for i in $(seq 1 36); do code=$(curl -s -o /dev/null -w '%{http_code}' -X POST -H 'Content-Type: application/json' -d '{"csl":".show cluster"}' http://localhost:9000/v1/rest/mgmt); [ "$code" = "200" ] && echo ready && break; sleep 5; done
   ```
   Port 9000 on the host, because Keycloak owns 8080 in the other tracks. If the container exits (`docker logs kusto`), note the error in CAVEATS and switch to the fallback path (F).
3. `builder`: layout and headers. `2h-detection-pack/detections/` holds one `<id>.kql` and one `<id>.yaml` per detection (same base name). YAML fields, all required: `id` (`TD-2H-01` …), `title`, `description` (two plain sentences), `tables` (`SigninLogs`, `AuditLogs`), `attack_technique_ids` (list; each entry is `TODO(verify)` unless the builder can quote the technique name exactly — never guess an ID), `al26_010_control` (the quoted AL26-010 recommendation it supports, e.g. "restrict and closely monitor MFA reset, recovery, and device re-enrolment processes"), `severity` (low/medium/high), `false_positive_notes` (which look-alikes could trigger it and why they should not), `expected_hits` (takeover ids from `fixtures/expected.json` this query must return), `expected_quiet` (look-alike ids it must not return). Minimum six detections, each ≤ 40 lines of KQL with a comment above every clause a beginner could not explain:
   - `TD-2H-01` helpdesk admin password reset followed within 24 h by a security-info (MFA method) registration for the same user.
   - `TD-2H-02` new MFA method followed by a successful sign-in from a device id or IP never seen for that user in the preceding 14 days.
   - `TD-2H-03` admin reset followed within 48 h by a privileged action (role membership add, `Core Banking Admin` app sign-in, recovery-email change).
   - `TD-2H-04` the full chain (reset → new MFA → new device → privileged action) joined on user with time windows, returning a `chain_score` (count of stages hit) and the stage timestamps.
   - `TD-2H-05` unusual reset volume: one helpdesk account performing more admin resets in a day than its own 14-day daily average plus a threshold (the precursor to a campaign).
   - `TD-2H-06` MFA change after a reset whose ticket note lacks the verification marker (`verified: callback to number on file`) — the control AL26-010 calls "out-of-band verification".
4. `builder`: the harness in `2h-detection-pack/tests/`:
   - `conftest.py`: session fixture `kusto`. Reads `KUSTO_URL` (default `http://localhost:9000`). Probes `POST <url>/v1/rest/mgmt` with `{"csl": ".show cluster"}`; if it is not HTTP 200: `pytest.skip` the module unless `KUSTO_REQUIRED=1`, in which case `pytest.fail` with the URL and the error. Connects with `azure-kusto-data`: `KustoConnectionStringBuilder.with_no_authentication(url)` → `KustoClient`; runs management commands with `execute_mgmt` and queries with `execute_query` (all three exist in azure-kusto-data 6.0.4). Creates database `mapleharbour` (`.create database mapleharbour volatile` — `TODO(verify)` against the emulator docs; if it fails, use the `persist` form with paths under `/kustodata`), creates tables `SigninLogs` and `AuditLogs` with a column per fixture field (`dynamic` for the object fields, `datetime` for `TimeGenerated`), ingests both fixture files with `.set-or-append <table> <| datatable(...)[...]` built from the JSON rows (batches of ≤ 100 rows; `.ingest inline` is an acceptable alternative), and verifies the row counts equal the file line counts before any test runs.
   - `test_2h_headers.py` (no emulator needed, runs in `checks`): every `.kql` has a `.yaml` with all required fields, ids are unique, `expected_hits`/`expected_quiet` reference ids that exist in `fixtures/expected.json`, every `TODO(verify)` is tagged exactly so.
   - `test_2h_detections_on_fixtures.py` (marker `kusto`): for each detection, run the query; assert the returned users ⊇ users of `expected_hits` and the returned users ∩ users of `expected_quiet` = ∅; assert every result row has a `UserPrincipalName` and a timestamp column.
   - `scripts/check_kql.py` (no emulator): static checks — balanced brackets and quotes, each referenced table name is `SigninLogs` or `AuditLogs`, each file ends with a projection of at least `UserPrincipalName` and a timestamp. Wire it into `test_2h_headers.py`.
   - `scripts/run_detections.py --url <KUSTO_URL> --data <dir> --out <file.jsonl>`: loads `<dir>/signin.jsonl` and `<dir>/audit.jsonl` into a fresh database, runs every detection and writes one alert per result row: `{alert_id, detection_id, title, severity, UserPrincipalName, TimeGenerated, evidence: {row fields}, source_correlation_ids}`. In this session it is run ONLY with `--data fixtures`. (The `kql` CI job will later run it over the full data, but only once `2e-blind-hunt/my-labels.json` exists — that guard is in `ci.yml`.)
5. `builder`: run the static tests: `ruff check .`, `pytest -q 2h-detection-pack/tests/test_2h_headers.py`.
6. Director (emulator path): `KUSTO_REQUIRED=1 pytest -q 2h-detection-pack/tests` must pass. Then prove the skip/fail logic: `docker stop kusto` → `pytest -q` passes with the kusto tests reported as skipped → `KUSTO_REQUIRED=1 pytest -q 2h-detection-pack/tests` fails with the "emulator unreachable" message → `docker start kusto`. Quote all three outcomes for the verifier.
   F (fallback path, no emulator here): write the same tests, run only the static ones locally, add a CAVEATS line (`TODO: emulator not runnable in cloud session, data tests run in the kql CI job only`), push the branch early so Eojin can open the PR and the `kql` job runs on GitHub's x86-64 runners; fix from its log in the same session while credit allows (at most two push–fix cycles). Fallback (a), Microsoft's free Azure Data Explorer cluster, only if Eojin approves creating it and adding its endpoint domain to the environment allowlist (Custom network) — not by default.
7. `chores`: `2h-detection-pack/README.md` table (id · what it catches · AL26-010 control · severity · false-positive notes · ATT&CK ids with their TODO state), plus the plain-English sections: how the harness works (create database → tables → ingest → run → assert), how to run it locally (emulator command from step 2, `KUSTO_URL`, `KUSTO_REQUIRED`), how CI runs it (`kql` job, why it is separate from `checks`), "What Claude did / what Eojin did", limits (fixtures are small and synthetic; thresholds are planning values; nothing has run against a real tenant). Validate every YAML header with pyyaml.
8. `verifier`: check the acceptance criteria, write `docs/verify/T2-S02.md`.
9. Director: `wrap`. Branch `t2-s02-detection-pack`.

## Known caveats
- Pin the emulator: after the pull, run `docker image inspect --format '{{index .RepoDigests 0}}' mcr.microsoft.com/azuredataexplorer/kustainer-linux:latest`, record the digest in `docs/PROBES.md`, and change the `kql` job's `image:` and the `docker pull` in `.claude/settings.json` to that same `@sha256:` digest in this PR, so a new `latest` can't break CI or the session mid-sprint. If the emulator can't run in this session, take the digest from the `kql` job's log on GitHub instead (`docker pull` prints `Digest: sha256:…`).
- The emulator needs an x86-64 CPU with AVX2 and does not run on ARM. `docs/PROBES.md` from T2-S01 tells you which path to take (`arch: x86_64` and `avx2 flags` > 0 and docker available = emulator path). GitHub-hosted runners are x86-64, so the `kql` job is the fallback.
- The image is pulled by the SessionStart hook in the background; a fresh session may still be pulling when the brief starts. Static work first, emulator second.
- `.create database … volatile` and the exact ingestion command syntax for the emulator are `TODO(verify)`; the builder should read the error text and adjust rather than guess.
- Exact Entra `OperationName` strings remain `TODO(verify)` from T2-S01; the detections match the generator's strings, which the README must say.
- `kql-paths` compares the PR's base and head commits; a PR that only changes `scripts/run_detections.py` will not trigger `kql`. Touch a file under `2h-detection-pack/` in that case.
- Time box and credit cap are planning numbers.
